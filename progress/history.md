## 2026-09-27 — Bug fix: registration/onboarding stuck on /onboarding after saving

- **Reported by the user:** after registering and completing the onboarding form, the app stayed on `/onboarding` instead of moving to `/calendar`.
- **Root cause, proven with an instrumented real-browser run (Microsoft Edge via Playwright) against the hosted project:** right after registering, the client pushes to `/calendar`; since onboarding is not done yet, the server correctly redirects that to `/onboarding`. Next.js's client-side router cache then remembers that outcome for `/calendar` in that browser tab. When onboarding later completes and the app pushes to `/calendar` again, the browser silently reused the old cached redirect and issued no new request at all for 90+ seconds. A full hard reload of `/calendar` worked immediately, proving the server was correct throughout and the bug was purely client-side caching.
- **Fix:** `completeOnboarding`, `signIn`, `register` and `signOut` in `lib/actions/onboarding.ts` and `lib/actions/auth.ts` now call `revalidatePath` (from `next/cache`) on their success paths for every route the client is about to navigate to, so Next.js invalidates its client-side cache for that route before the redirect happens. `signIn`/`signOut` were fixed proactively for the identical latent risk (switching users or roles in the same browser tab), not because they were reported broken.
- **Verification:** `bash init.sh` exit 0, 504/504 tests (new assertions added inside existing tests, so the count did not change), `pnpm build` passes. Reviewer APPROVED with no required changes, having traced every branch to confirm `revalidatePath` is called only on true success paths and never on error or rollback paths. **Live verification by the leader, real Edge browser via Playwright against the hosted project:** two consecutive register -> onboarding -> reach `/calendar` runs succeeded (11 to 13 seconds end to end, `/calendar` requested immediately after the onboarding save); the existing login and logout flows still work with no regression; a same-tab logout-then-login-as-a-different-role scenario showed no stale cached content from the previous session.
- **Process note:** unlike every other verification in this session, this required a real browser, not HTTP-level Server Action calls, because the bug lived entirely in the browser's router cache. The feature #11 live check that marked onboarding "done" could not have caught this, since it called the action directly over HTTP rather than through a real client-side navigation; that is a real gap in how this class of bug gets caught, worth keeping in mind for future features that navigate after a mutation.
